Verification

Verification checks a whole program before it runs. A verified program can’t hand an instruction an operand of the wrong type, underflow the operand stack, call a function with the wrong arguments, return the wrong values, or reach a join point with an inconsistent stack. The runtime still checks heap tags, bounds, and freed objects, because some facts only exist at run time.

Each component supplies a typing rule for its instructions, and the framework does the rest: it finds the basic blocks of each function, walks them to a fixpoint, merges stack states where paths join, and reports every problem at once. A machine can only be verified if every instruction in it has a rule, and the compiler checks that.

Verification lives in the vihaco::verifier module (the vihaco-verifier crate). The program-image-execution feature includes it; enable the verifier feature to use it on its own.

Verifying a program

An image only accepts a Verified module, so verification is part of loading. (With typed-declarations alone, without program-image-execution, programs run through the legacy ProgramImage, which does not require Verified: there, verification happens only if you call verify_module before loading.)

let module = metadata.into_module(code)?;   // parse and lower as usual
let image = Image::new(Verified::new(module)?);
let mut loaded = Loadable::new(image, machine);

Verified::new returns a Rejection if the program has any error. Its diagnostics list every finding, sorted by function and address, and it converts into an eyre::Report whose message lists them all. Use Verified::verify to choose options and keep the result: it returns the verified module together with a Verification holding any warnings (code no path reaches is reported as Unreachable, a warning, not an error) and, if you asked for them, type maps.

The example below gives a small mixing device typing rules, then verifies one good and one bad program. Setup that isn’t about verification (parsing the source, and execution, which this page doesn’t need) is folded away.

use vihaco::{
    Execute, HasInstructionSet, Type, Value, Verified, Verify, component, composite, dialect,
    module::{LocalModule, ProgramMetadata},
    verifier::{DiagnosticKind, OperandStack, TypeSlot, TypedSlot, VerifyOptions, stack_effect},
};

#[dialect]
pub mod mixer {
    /// `[f64, f64] -> [f64]`: multiply two samples.
    #[instruction]
    #[pattern = "'scale_f64"]
    pub struct ScaleF64;

    /// Pop `n` samples and push their sum. The count is an immediate operand.
    #[instruction]
    #[pattern = "'sum_f64 $0"]
    pub struct SumF64(pub u32);
}

#[component]
#[instructions { mixer }]
#[derive(Default)]
pub struct Mixer;

impl<C> Verify<C> for mixer::ScaleF64
where
    C: OperandStack + ?Sized,
    C::Slot: TypedSlot,
{
    fn verify(&self, cx: &mut C) -> eyre::Result<()> {
        stack_effect(cx, [Type::F64, Type::F64], [Type::F64])
    }
}

impl<C> Verify<C> for mixer::SumF64
where
    C: OperandStack + ?Sized,
    C::Slot: TypedSlot,
{
    fn verify(&self, cx: &mut C) -> eyre::Result<()> {
        for sample in cx.pop_n(self.0 as usize)? {
            sample.expect(&Type::F64)?;
        }
        cx.push(C::Slot::of_type(Type::F64));
        Ok(())
    }
}

#[composite]
pub struct Machine {
    #[device(0)]
    #[program]
    execution: vihaco_stdlib::ExecutionState,
    #[device(1)]
    mixer: Mixer,
}

type Program = LocalModule<<Machine as HasInstructionSet>::Runtime, Value, Type>;

fn main() -> eyre::Result<()> {
    let good = load(&[
        "execution::program::const_f64 1.5",
        "execution::program::const_f64 2.0",
        "mixer::mixer::scale_f64",
        "execution::program::const_f64 0.5",
        "mixer::mixer::sum_f64 2",
        "execution::program::ret 1",
    ])?;
    let options = VerifyOptions::default().with_type_maps(true);
    let (verified, verification) = Verified::verify(good, options)?;
    assert!(verification.warnings.is_empty());
    assert_eq!(verified.code.len(), 6);

    // Type maps hold the converged state at each block's first instruction.
    let maps = verification.type_maps.expect("requested");
    assert_eq!(maps.get(0, 0).unwrap().operands(), &[] as &[TypeSlot]);

    // `scale_f64` needs two `f64` samples, but finds a `u64` below the top.
    let bad = load(&[
        "execution::program::const_u64 3",
        "execution::program::const_f64 2.0",
        "mixer::mixer::scale_f64",
        "execution::program::ret 1",
    ])?;
    let rejection = Verified::verify(bad, options).unwrap_err();
    let [error] = rejection.diagnostics.as_slice() else { panic!("{rejection}") };
    assert_eq!((error.function, error.address), (0, 2));
    assert_eq!(
        error.kind,
        DiagnosticKind::TypeMismatch { expected: "f64".into(), found: "u64".into() }
    );
    assert_eq!(
        error.to_string(),
        "error: function 0 at 2: type mismatch: expected f64, found u64"
    );
    // Rejections carry type maps too, so a tool can show types next to errors.
    assert!(rejection.type_maps.is_some());
    Ok(())
}

Diagnostics

Each Diagnostic names the function (its index in the function table), the instruction address, a severity, and a DiagnosticKind. The structured kinds cover the framework’s checks: StackUnderflow, StackDepthMismatch (two paths reach a join with different depths), TypeMismatch, CallArityMismatch, ReturnCountMismatch, LocalIndexOutOfRange, InvalidControlFlowTarget, InvalidFunctionSpan, MissingTerminator, Unverifiable, and the warning Unreachable. Any other error a rule returns is reported as Rule with its message.

A failing rule ends its basic block, so a block reports at most one rule error and code reachable only through it isn’t analysed. A block that fails is checked against the paths that don’t run through another failing block, so a diagnostic never stems from a state some other defect produced. Each defect is reported once, even inside a loop.

Type maps

With VerifyOptions::with_type_maps(true), both a Verification and a Rejection carry TypeMaps: the converged state (locals and operand stack) at the first instruction of each reached block. The state at any other address is one block replay away, which is what a debugger or observer needs to show what each stack slot holds at a breakpoint. In a rejection, blocks that were only reachable through a failing block have no entry.

Without a Verified wrapper

verify_module(&module, options) verifies a borrowed module without consuming it, which is handy in tests. ModuleVerifier is the standard context behind both: it reads the module’s function, struct, named-type, constant, and string tables.

Verified::assume_verified(module) skips verification explicitly. Use it for tests that exercise runtime checks with deliberately ill-typed programs, for modules a trusted toolchain has already verified, and for module models the standard verifier doesn’t cover. Keep it easy to find: it is the one place an unverified program can reach an image, outside the typed-declarations-only build described above. (The low-level runner, vihaco::execution_state::{execute, resume}, runs a plain module without an image and without verification; reach for it only for trusted code.)

Writing typing rules

A rule implements Verify<C> for an instruction type. C is the verifier context, and the rule names only the capabilities it needs as bounds, never a concrete verifier. That keeps rules usable in any machine, and a missing rule or capability is a compile error naming the instruction.

pub trait Verify<C: ?Sized> {
    /// Where control goes after this instruction; `Flow::Next` by default.
    fn flow(&self) -> Flow { Flow::Next }
    /// Check the inputs against the abstract state in `cx` and update it.
    fn verify(&self, cx: &mut C) -> eyre::Result<()>;
}

Only control-flow instructions override flow: Flow::jump(target) for a branch, Flow::jump_to([a, b]) for a conditional one, Flow::Return and Flow::Halt for terminators. flow must depend only on the instruction’s own operands, because the verifier uses it to find blocks before any state exists.

The standard capabilities, all provided by ModuleVerifier:

CapabilityProvides
OperandStackpop, pop_expect, pop_n, push, peek, depth over TypedSlot slots
Localsthe function’s declared locals, local(i) and set_local(i, slot)
Signatures<Type>function signatures by index or address, and the current function’s
StructTypes<Type>field counts and field types from the struct table
NamedTypes<Type>named-type indices by name, and their representations
Constants<Value, Type>the constant and string tables

stack_effect(cx, [inputs], [outputs]) covers every fixed-signature instruction. For instructions several dialects share there are helpers that keep rules identical: call_effect and return_effect, direct_call_effect and indirect_call_effect, load_local and store_local, string_constant, function_constant, and pop_array. A call-like instruction must use call_effect, direct_call_effect or indirect_call_effect, or call Signatures::after_call after its operand effect, so component state is reset after the call (see Component state).

A conflicting slot, left where two paths disagreed about a type, never satisfies a typed pop. Named types are nominal: type 0 satisfies only itself.

Counts must be immediates

The verifier only sees the program text, so an instruction’s stack effect must follow from its operands. Carry counts and shapes as immediate operands, as sum_f64 2 does above. When an instruction takes its operand count from a runtime value (say, a count popped from the stack), its rule should report it with VerifyError::unverifiable(reason), which produces the standard Unverifiable error rather than an ad-hoc message:

use vihaco::{
    Type, Verify,
    verifier::{OperandStack, TypedSlot, VerifyError},
};

/// Pops a `u64` count, then that many samples: not statically checkable.
pub struct SumDynamic;

impl<C> Verify<C> for SumDynamic
where
    C: OperandStack + ?Sized,
    C::Slot: TypedSlot,
{
    fn verify(&self, cx: &mut C) -> eyre::Result<()> {
        cx.pop_expect(&Type::U64)?;
        Err(VerifyError::unverifiable("`sum_dynamic` pops its sample count from the stack").into())
    }
}

Component state

Some correctness facts aren’t about operand types: a sequencer may need a channel opened before it plays on it. Such a component defines its own capability trait and abstract state. The state implements ComponentState, whose join merges the states of two paths (a channel is open after a join only if it is open on every path) and must have finite height. The framework’s WithState<'_, S> context wraps ModuleVerifier, joins S alongside the frame, and the component crate implements its capability for it:

use std::collections::BTreeSet;
use vihaco::{
    Verify,
    verifier::{ComponentState, VerifyError, WithState},
};

/// The sequencer's capability: channels must be opened before use.
pub trait Channels {
    fn open(&mut self, channel: u32);
    fn require_open(&self, channel: u32) -> Result<(), VerifyError>;
}

#[derive(Clone, Default)]
pub struct Open(BTreeSet<u32>);

impl ComponentState for Open {
    fn join(&mut self, incoming: &Self) -> Result<bool, VerifyError> {
        let before = self.0.len();
        self.0.retain(|channel| incoming.0.contains(channel));
        Ok(self.0.len() != before)
    }

    /// Nothing is assumed open after a call, the same as at a function entry.
    fn after_call(&mut self, _callee: Option<u32>, entry: &Self) {
        self.clone_from(entry);
    }
}

impl Channels for WithState<'_, Open> {
    fn open(&mut self, channel: u32) {
        self.state_mut().0.insert(channel);
    }
    fn require_open(&self, channel: u32) -> Result<(), VerifyError> {
        if self.state().0.contains(&channel) {
            Ok(())
        } else {
            Err(VerifyError::rule(format!("channel {channel} is not open")))
        }
    }
}

/// `play c`: the rule needs only the `Channels` capability.
pub struct Play(pub u32);

impl<C: Channels + ?Sized> Verify<C> for Play {
    fn verify(&self, cx: &mut C) -> eyre::Result<()> {
        Ok(cx.require_open(self.0)?)
    }
}

An embedder then verifies with Verified::verify_with_state(module, Open::default(), options), which starts every function with that state. A machine whose components each add state combines them as a tuple.

Component state does not flow through calls. Each function is verified separately from the entry state, so the entry state must assume nothing a caller might not have set up (here: no channels open). After a call, the caller’s state becomes ComponentState::after_call, which every state must define: the callee may have changed anything, so the result must assume no more than any callee could leave behind. Open resets to the entry state:

open 1
call 0, @helper   // the caller's state is reset: channel 1 is no longer open
play 1            // rejected: channel 1 is not open

A helper therefore cannot rely on a channel its caller opened; open channels in the function that plays on them, or after the call.

Resetting to the entry state is right for Open because “no channels open” is safe whatever the callee did. It is wrong for a state that accumulates, such as the time elapsed against a deadline: its entry state is “0 elapsed”, but a callee may wait any amount, so resetting would accept wait 2; call 0, @helper; deadline 10 even when the helper waits 50. Such a state must become “unknown” after a call. That is why after_call has no default: there is no answer that is sound for every state.

The call helpers, call_effect and indirect_call_effect, apply after_call for you. A custom call-like rule must use them, or call Signatures::after_call itself after its operand effect. Per-callee summaries are a possible future extension.
